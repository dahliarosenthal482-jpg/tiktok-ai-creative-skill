# Script Package Framework v1.0

Framework ID: VP-US-005C-SPF-v1.0

Task ID: VP-US-005C

Executor: WORK-CREATIVE-001

Status: EXECUTED — WAITING SUPERVISOR REVIEW

Scope: Reusable schema converting an approved Creative Production Specification Production Intent into a future Script Package Content Structure Contract for a separate Video Production Specification. This framework contains no production parameters, real product script, advertising copy, spoken line, caption, finished Hook, storyboard, shot list, scene timeline, AI Prompt or Generation Task.

## Framework flow

`Creative Strategy → Creative Production Specification → Script Package → Video Production Specification → Creative Review → WORK-VIDEO-001 → Generation Task`

A Script Package is a structured content-organization record. It consumes an approved Production Intent and defines how that intent is organized into Content Logic. It outputs a bounded Content Structure Contract to the Video Production Specification layer. It cannot redefine Product Truth, Audience Direction, Creative Objective, Business Objective, Content Goal, claim restrictions or evidence classifications. It cannot contain production parameters or be handed directly to WORK-VIDEO-001.

# 1. Script Metadata

Every future Script Package must contain:

|Field|Requirement|
|---|---|
|Script ID|Stable unique identifier|
|Script Structure ID|Versioned identifier for the selected logical structure|
|Version|Immutable reviewed version; material changes create a new version|
|Market|Reference the approved Specification; do not infer|
|Product Reference|Reference the approved product source; do not restate or expand facts|
|Creative Production Specification ID|Exact approved Production Intent source ID and version|
|Language|Declared production language and locale|
|Content Objective|Reference one approved objective category and its intended job|
|Content Type|Reference an approved content type|
|Created By|Responsible Creative Agent|
|Approval Status|`DRAFT`, `INCOMPLETE`, `APPROVED`, `NEEDS_REVISION`, or `REJECTED` as applicable|
|Approved By|Authorized reviewer only; never self-issued by the executor|
|Review Reference|Controlling review record for the exact version|

Metadata does not authorize automatic population of creative content.

# 2. Script Objective

Translate the approved Production Intent into one primary content-organization objective. Supporting objectives are allowed only when the approved Creative Production Specification requires them.

|Objective Type|Viewer Goal|Business Goal|Measurement Direction|
|---|---|---|---|
|Awareness|Recognize relevance, category or topic|Generate qualified attention|Impressions, qualified Views, hold or thumb-stop metrics when available|
|Interest|Understand the central idea or product role|Support deeper viewing or information seeking|Watch progression, average watch time, completion or detail interaction|
|Consideration|Evaluate fit, proof, value or trust|Support a qualified decision process|Product-detail interaction, saves, questions or add-to-cart when available|
|Conversion|Resolve final decision friction and identify the permitted action|Support an attributable action without false urgency|Orders, conversion rate, verified clicks or approved commerce metrics|
|Retention|Create a reason to continue, return or follow a series|Support repeat engagement or structured learning|Return viewing, series progression, repeat engagement or retention metrics|

Future packages fill only objective references approved upstream. This framework does not assign a concrete objective to any product.

# 3. Audience Trigger Framework

Trigger categories describe psychological functions, not finished audience language.

|Trigger Category|Function|Required Boundary|
|---|---|---|
|Problem Recognition|Establish relevance through an approved audience concern|No shame, invented pain point or universalization|
|Curiosity|Create an information gap that will be truthfully resolved|No clickbait disconnected from approved information|
|Value Understanding|Clarify why approved information may matter to the audience|No invented value, savings or superiority|
|Trust Building|Reduce uncertainty through traceable evidence and restraint|No fabricated testimonial, authority or guarantee|
|Objection Removal|Address an approved concern within its evidence boundary|No unapproved answer, troubleshooting or product claim|
|Social Proof|Use verified, permissioned social evidence when explicitly approved|No invented comment, reviewer, metric or consensus|

Packages select categories and record source references. They do not generate pain-point wording.

# 4. Information Flow Framework

Canonical logical flow:

`Attention → Context → Problem / Desire → Product Understanding → Proof → Objection Handling → Action`

|Flow Function|Required Planning Field|
|---|---|
|Attention|Opening Objective and chosen trigger category|
|Context|Minimum information needed for relevance and comprehension|
|Problem / Desire|Approved audience need or desired decision state by source reference|
|Product Understanding|One approved communication priority|
|Proof|Proof type, source, permission and presentation boundary|
|Objection Handling|Concern category, permitted evidence and prohibited interpretations|
|Action|Decision-stage purpose and compliance boundary|

Functions may be omitted or combined only when the approved objective and Specification permit it. This is logical structure, not narration, timing, scenes or copy.

# 5. Hook Framework

|Hook Type|Strategic Function|Required Control|
|---|---|---|
|Curiosity Gap|Create a truthful reason to seek resolution|The later information must resolve the gap|
|Demonstration First|Use permitted visual proof to establish immediate understanding|Requires approved proof and physically valid demonstration boundaries|
|Question Based|Frame a relevant information need|Do not fabricate a real audience question or commenter|
|Problem Based|Establish relevance through an approved concern|Do not dramatize, shame or universalize|
|Unexpected Result|Highlight a verified contrast or result only when explicitly approved|Blocked without approved result evidence; never imply guarantees|
|Comparison|Simplify a permitted decision context|No unsupported superiority, parity or competitor disparagement|
|FAQ Response|Address an approved uncertainty|No fabricated social proof or response wording|

The future package records `Opening Objective`, Hook type, evidence source, resolution requirement and risk. It must never contain a finished Hook sentence under this framework task.

# 6. Message Framework

|Message Module|Definition|Required Source Control|
|---|---|---|
|Core Message|One approved communication priority the future script must convey|Specification and Strategy reference|
|Supporting Information|Only information necessary to understand or substantiate the core message|Approved factual/evidence source|
|Proof Requirement|Proof type, source, permission and minimum verification condition|Traceable evidence record|
|Trust Element|Mechanism for credibility, transparency or expectation setting|Approved evidence and claim boundary|
|Risk Handling|Known ambiguity, claim risk, audience risk or production risk to avoid or disclose|Specification Risk Items and restrictions|

This framework defines module fields only. It does not populate product selling points, claims or message copy.

# 7. Proof Framework

|Proof Type|Permitted Purpose|Admission Requirement|Boundary|
|---|---|---|---|
|Product Demonstration|Make an approved function or physical relationship understandable|Approved Product Reference and usage boundary|Demonstration is not proof of outcome or creative effectiveness|
|Usage Example|Show a plausible approved context|Approved scenario and source classification|Example is not universal guidance or guaranteed suitability|
|Customer Signal|Represent a traceable customer observation|Source, sample boundary and permission|Customer Insight is not Product Truth or universal behavior|
|Feature Explanation|Clarify an approved factual feature|Approved Product Truth reference|No added function, performance or superiority claim|
|Comparison Context|Provide a permitted decision frame|Approved comparison dimensions and evidence|No unverified parity, ranking, savings or disparagement|

Proof type does not mean the proof has been validated as an effective creative mechanism. Each package must record `Observed Evidence`, `Inference` or `Future Test Direction` status.

# 8. Objection Handling Framework

|Objection Category|Planning Requirement|Prohibited Output|
|---|---|---|
|Price|Record verified offer source, validity and permitted value boundary|Invented regular price, savings, scarcity or purchase line|
|Ease of Use|Record approved usability evidence and uncertainty|Universal ease, safety or suitability guarantee|
|Product Understanding|Identify the exact comprehension gap and approved explanation source|Unapproved instruction or invented feature|
|Trust|Identify the evidence, provenance or expectation boundary needed|Fabricated authority, review, testimonial or certainty|
|Expected Result|Record permitted expectation and forbidden outcome claims|Medical, transformation or guaranteed-result response|

A future package identifies the concern, source boundary, evidence needed and unresolved risk. It does not generate response wording.

# 9. CTA Framework

CTA categories define action purpose, not copy.

|CTA Purpose|Intended Decision Job|Compliance Boundary|
|---|---|---|
|Learn More|Invite further verified information review|No implied result or hidden condition|
|Try Product|Invite consideration or trial only when the approved channel and offer permit it|No universal suitability or guaranteed experience|
|Check Offer|Direct attention to a current verified offer|Offer, availability and expiry must be reverified|
|Reduce Hesitation|Encourage review of approved proof, fit or policy information|No fabricated reassurance or urgency|
|Explore Solution|Invite evaluation of an approved product role or category|No medical framing or guaranteed resolution|

Each future package records CTA Purpose, destination, required verification and prohibited implication. It must not contain purchase copy.

# 10. Script Constraint

Every future Script Package must inherit and preserve:

- Product Truth: factual statements reference the approved Product Reference; missing facts remain missing.
- Claim Compliance: approved claims and forbidden claims are versioned source references.
- Platform Compliance: language, disclosure, social-proof, offer and prohibited-content rules are recorded for the target platform.
- Audience Alignment: audience needs remain within approved evidence and targeting boundaries.
- Product Lock: product identity, variant, component and visual restrictions cannot be weakened.
- Role Lock: identity-dependent content is blocked without a valid approved Role Reference.
- Scene and Proof Boundaries: physical plausibility and source permission are mandatory.
- Evidence Classification: hypothesis, inference and observed evidence remain distinguishable.

Forbidden: unapproved functions, effects, medical claims, result guarantees, invented evidence, fabricated comments/testimonials, unsupported comparisons and any source conflict silently resolved by the package.

Missing required sources set the Script Package to `INCOMPLETE` and block review approval.

# 11. Script Package Output Contract

The sole downstream object of a Script Package is a new, versioned `Video Production Specification`. The Script Package output is a `Content Structure Contract`. It must not be passed directly to WORK-VIDEO-001 and cannot create, request or authorize a Generation Task.

|Output Field|Content-Organization Value Passed Forward|
|---|---|
|Script Package ID / Version|Exact immutable source identifier|
|Creative Production Specification Reference|Exact approved Production Intent source ID and version|
|Creative Strategy Reference|Traceable upstream Strategy reference inherited through the Creative Production Specification|
|Script Objective|Primary objective, Viewer Goal, Business Goal and Measurement Direction|
|Script Structure ID|Selected logical structure identifier|
|Information Flow|Ordered logical functions without wording or timing parameters|
|Audience Trigger|Selected category, source classification and boundary|
|Content Type Direction|Content-format intent for production translation, not a production setting|
|Message Framework|Core communication priority and supporting-information requirements|
|Proof Logic|Proof type, source, permission, classification and unresolved limitation|
|Objection Handling|Concern category, permitted evidence and prohibited interpretations|
|CTA Purpose|Action purpose, destination class and verification requirement without CTA copy|
|Claim Boundary Reference|Approved claim source and prohibited-claim reference|
|Evidence Classification|Observed Evidence, Inference or Future Test Direction for every populated input|
|Risk Items|Unresolved content, evidence, permission and compliance risks|

The Video Production Specification layer translates this Content Structure Contract into AI Production Requirements. That transformation must preserve the upstream Creative Objective, Audience Direction, Business Objective and Production Intent as well as Script Objective, information order, proof logic, claim boundaries and evidence status without adding unsupported facts.

## Script Package prohibitions

A Script Package must not contain:

- Provider or Adapter selection.
- Model selection or version.
- Camera parameters, lens values, frame rate, resolution or provider syntax.
- Visual-generation parameters or motion-generation parameters.
- Prompt text or Prompt modules.
- Generation Task fields, lifecycle state or API payload.
- Production-ready Scene commands, Storyboard, Shot List or Scene timeline.

If any such production field is required, it belongs in the separate Video Production Specification or later authorized production layers, never in the Script Package.

# 12. Evidence Classification

Every populated future field must carry one classification:

|Classification|Meaning|Permitted Use|
|---|---|---|
|Observed Evidence|Directly supported by an approved, traceable source|May support factual structure within the exact source boundary|
|Inference|Reasoned interpretation of approved evidence|May guide planning when labeled; cannot become Product Truth or causal fact|
|Future Test Direction|Unvalidated hypothesis selected for evaluation|May define a test variable; cannot be described as proven or winning|

Required evidence metadata: Source Reference, Source Version, Approval Status, Evidence Class, Permission Status, Limitations and unresolved conflicts.

Test hypotheses must never be written as facts. Performance association must never be written as creative causality without appropriate evidence.

# 13. Review Requirement

Every Script Package requires independent Creative Review for the exact version.

## Review checks

- Strategy Alignment
- Specification Alignment
- Product Truth and Product Lock
- Audience Match
- Objective and Information Flow coherence
- Proof provenance and permission
- Claim and Platform Compliance
- Role and Scene reference validity
- Evidence classification integrity
- Production feasibility and unresolved Risk Items

## Decisions

- `APPROVED`: the exact Script Package version, tied to an approved Creative Production Specification, may be used to create a Video Production Specification. It may not enter WORK-VIDEO-001 directly.
- `NEEDS_REVISION`: correctable issues exist; no WORK-VIDEO-001 handoff is allowed.
- `REJECTED`: source, strategy, claim, permission or feasibility conflict prevents handoff.

Execution status does not equal approval. The executor may not self-approve. Script Package approval authorizes only the next specification-conversion step; it does not approve a Video Production Specification, WORK-VIDEO-001 intake, Prompt, Generation Task, provider call or generated asset.

## Framework evidence boundary

### Observed Evidence

- System standards define the Creative Production Specification as the only generation handoff and define the Script Framework as logical jobs rather than creative copy.
- Supervisor Review `8e4a196053290b890b598b73dc20c2e2547e2c58` requires the Script Package to sit between Creative Production Specification and Video Production Specification with non-overlapping authority.
- The approved upstream project records retain Product, Role, Scene, claim, evidence and generation-admission boundaries.

### Inference

- A normalized Script Package schema can reduce ambiguity between strategy and content organization when its downstream object is explicitly limited to a Video Production Specification.
- Separating objective, trigger, information flow, proof, objection and CTA purpose may make reviews more traceable.

### Future Test Direction

- Validate this schema through separately authorized packages without changing the framework fields silently.
- Add or revise fields only through a versioned review cycle after repeated workflow evidence.

## Risk Items

- This framework is not a populated Script Package and cannot be used as finished creative or production input.
- Source standards retain executor-time waiting-review labels; controlling Supervisor records govern project approval.
- A role-dependent future package remains blocked without an approved Role Reference.
- Packaging proof remains blocked without an approved packaging reference.
- Video Intelligence remains `PARTIAL COMPLETE`, Quality A = 0; no Hook, scene, timing, character, style or CTA may be treated as proven.
- Video Production Specification approval, model selection, budget authorization, Prompt Contract, provider route and Generation Task remain separate downstream gates.
